Why a support agent's memory should be a graph — the problem, the decisions, the receipts

This is not a product announcement. It is the log of how we decided what to build for a 36-hour hackathon, written while we built it. If you want the code, it is TODO: repo link. If you want the thinking, read on.

The problem

Watch a support agent take a ticket. Any support agent, any helpdesk.

The ticket says "money deducted, order not placed." Before the agent can type a single useful word, they open the CRM to see who this customer is. The billing panel to confirm the deduction. The ticket history to learn this is the customer's third attempt. An internal chat to ask whether anyone else has seen this today. A knowledge base that may or may not have been updated since the last release. Five systems, and the customer is still waiting.

The context exists. All of it. It is just stored in pieces that do not know about each other, so a human reassembles it, per ticket, forever. The senior agents are fast only because they carry the missing links in their heads — which release broke what, which team owns which screen, which workaround actually works. When they leave, the links leave.

So the problem statement, in one line: every ticket starts from zero, because the relationships between customer, history, cause, and fix live nowhere.

Most AI support tools attack the typing: draft the reply faster. We think that is the wrong end of the ticket. The expensive part is not writing the answer. It is assembling the context that makes the answer right.

The shape of the problem

Look at what support actually asks, and notice none of it lives in one record.

  • What did this customer try before, and did it work?
  • What fixed the last fifty tickets that look like this one?
  • Which release caused this spike?
  • Who on the team has solved this class of problem before?

Every one of these is a question about connections. Relationships are the data. Which is the whole argument for storing them as a graph — nodes and edges the agent can walk — instead of as prose it has to re-derive every time.

But "we think" is not evidence. The rest of this post is us trying to falsify our own idea.

Decision log

01 · sat 12:00

Build the context layer, not another reply-drafter

The thesis as a contrast: not faster typing — zero cold starts. One agent, one job: handed a ticket, produce a briefing that already contains who the customer is, their history, the five most similar resolved tickets and what fixed them, the likely cause, and the owning team — with the path it walked to get there shown, so a human can check it.

rejected: reply drafting, gamification, real-time calls. all real ideas, all cut, because a briefing that is wrong fast is worse than one that is right.

02 · sat 12:10

Don't claim the graph is cheaper. Measure it.

Four memory architectures, one dataset, same model, same questions: (A) stuff everything into the prompt, (B) vector top-k, (C) flat file memory, (D) a FalkorDB graph. Count input tokens, time retrieval, score answers. Publish the harness so anyone can re-run it.

cost: ~6 hours we could have spent on features. why paid: without numbers this post is an opinion.

03 · sat 12:20

Implement Devin's memory spec as the fair baseline

You cannot benchmark a closed product. But Devin's memory is built on an open spec — a git repo of Markdown notes, a MEMORY.md index loaded each session, one-line entries with sources, a nightly dream that consolidates. So baseline C is a faithful implementation of that spec, not a strawman. If the graph cannot beat a competent filing cabinet, we want to know.

04 · sat 12:30

TypeScript + Pi Durable over Python + Graphiti

The comfortable path was Python with Graphiti on FalkorDB — temporal knowledge-graph memory, contradiction handling included. We took the other path: TypeScript on Pi Durable, an experimental harness where every step of a run is a checkpointed task that survives the process dying — and raw, hand-written Cypher against FalkorDB.

gave up: Graphiti's free temporal logic. got: an agent you can kill -9 mid-ticket that resumes from its checkpoint, and every query in the repo readable by a human. risk accepted: Pi Durable is experimental and we learned it during the event.

Temporal invalidation, by hand

Memory that cannot forget correctly is not memory, it is a liability. When a fact changes — the bug is fixed, the customer upgraded — we do not delete the old edge. We stamp it:

// a contradicted fact is retired, not erased
MATCH (c:Customer {id: $id})-[r:ON_PLAN]->(:Plan)
WHERE r.valid_until IS NULL
SET r.valid_until = timestamp()
WITH c
MATCH (p:Plan {name: $newPlan})
CREATE (c)-[:ON_PLAN {valid_from: timestamp(), valid_until: null}]->(p)

Live queries filter valid_until IS NULL. History stays walkable; the agent just stops serving it. This is the eight lines Graphiti would have given us for free. It was worth writing once.

Dreaming is a background task, not a cron job bolted on

Pi Durable has background tasks that belong to a conversation but not its current work. So the dream — replay the day's tickets, cluster them with FalkorDB's community detection to surface emerging issues, promote repeated fixes into procedural memory, retire contradicted edges, write the morning briefing — is just another durable task. It survives restarts like everything else.

07 · sat 12:11

Three memory tiers, and the company tier is append-only for everyone

One FalkorDB instance, three kinds of graphs: company (the brain), team_*, user_* — multigraph makes each a real, isolated graph, not a filter. The company tier is written by exactly one actor, the dream, and only ever by appending: a wrong fact is retired with a timestamp, never edited. Humans and their conversations get read-only access to it, enforced in the harness loadout — the write tool simply is not in their toolset.

why: a shared brain that anyone can silently edit is not a brain, it is a wiki war. append-only is what makes it trustworthy enough to share.

08 · sat 12:11

Doctrine vs practice: let the graph catch the company lying to itself

The company brain holds two kinds of truth. Doctrine: what the docs claim — "withdrawals take 24 hours." Practice: what the tickets show — the last 40 withdrawals took 71. Because both live in the same graph, the mismatch is not an insight someone has in a retro six weeks late. It is an edge, computed nightly by arithmetic, with the ticket IDs as evidence, routed to the team that owns the doc.

rule: detection is deterministic — a promised number against a measured one needs Cypher, not a model. the LLM only writes the suggestion's prose, and a suggestion is a hypothesis with receipts, never an auto-applied fact.

09 · sat 12:13

Every graph use pays rent

Graphs are fashionable, which is exactly why we do not get to use them on vibes. Every feature that touches the graph gets a row in a feature ledger: what it does, what we measured it against, and the result — good or bad. A feature we did not measure says "not measured" in public. The best example: the mismatch engine's rules run against an LLM handed all the docs and tickets as raw text, on five planted mismatches we know the answers to. If the expensive way finds things the cheap way misses, that goes in the post too.

The crash test

An always-on agent is an agent that survives dying.

  1. A ticket arrives; the agent starts assembling the briefing.
  2. We kill -9 the process between two tool calls.
  3. A new process opens the same storage.
  4. The interrupted run continues from its checkpoint — the safe graph reads rerun, the rest resumes.
  5. The briefing arrives. The memory graph never noticed.

FAQ

Why not just a vector database?
We tried. It is baseline B. See fig 2.

Is this a shot at Devin?
No. Their spec is open and good at what it is for — personal preferences and project gotchas. Support context is a different shape of problem. That is the point of measuring instead of asserting.

Why is there a SQLite file in a graph project?
Two storage roles. FalkorDB holds what the agent knows — the memory this whole post is about. SQLite holds what the agent is doing — Pi Durable's transcripts and task checkpoints, which is what the crash-resume runs on. The harness storage interface is small enough that FalkorDB could plausibly hold both over its Redis protocol; we were not going to hand-roll the storage under our own crash demo in 36 hours. It's in LATER.md.

Why is the dataset synthetic?
Hackathon rules, and basic hygiene: no real customers in a public demo. The generator is seeded and in the repo; the fictional company's dysfunctions are statistically modeled on public accounts of support-team pain, not on anyone's data.
