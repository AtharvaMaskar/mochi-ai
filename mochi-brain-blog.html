Why I built this

I'm an AI engineer at a stock-broking platform. This project comes from a problem I see at work every day.

A customer can be onboarded in a day or two. Behind that, support depends on many teams: onboarding, KYC, the KRA and more. Every hand-off between them is manual. Every new ticket starts from zero.

I also wanted to explore agent memory. It is one of the least explored parts of agentic systems. Most agents keep memory in markdown files. That never sat right with me: it burns tokens. Here I could finally measure it.

Honest take on FalkorDB: I thought it was just another graph database. Then I found graph algorithms as tools. The graph does the joining, ranking and clustering. The model picks the tool and writes the sentence. That was the missing link for me.

So I built mochi: a support desk whose whole memory is one FalkorDB graph, where every answer shows the path it walked. All data on this page is synthetic. E Corp Securities is a fictional broker.

The rest is the decision log of one build day. The first commit landed at 10:35 IST. Each entry has a timestamp from git, the question, what I rejected and what it cost. Every figure is read from bench/results.json. I don't type numbers by hand. The code is at github.com/AtharvaMaskar/mochi-ai.

The headline

We want a small model to be enough, because the memory carries the weight. In mochi, Haiku answers from the graph.

Haiku on the graph: correct, at per answer. Sonnet on markdown notes: , at . Same questions. Same judge.

The gap is multi-hop. "Which release caused the issues behind this week's refund tickets?" On Haiku, the graph got of those right. Markdown notes got . SQLite tables with the same queries got . Tables are the honest rival. Edges still won.

Then the bill for keeping notes. Turning the tickets into markdown memory took tokens. The graph's extraction took . When a fact changes, a model rewrites the notes: tokens per change, on average. The graph closes the old fact with a date, in one Cypher write: tokens.

And staleness. After the facts changed, the graph answered with the current fact on questions. The notes managed . A note doesn't know it stopped being true.

Where it lost, up front: on Haiku, notes, tables and vector top-k are all cheaper per answer than the graph. All three are wrong more often. The full list is in Where I lost.

The problem

We want a support agent to start every ticket knowing what the company already knows. In mochi, the agent gets a briefing before it types a word.

Watch a support agent take a ticket. "Money deducted, order not placed." Before they can write anything useful, they open the CRM to see who this is. Then billing, to confirm the debit. Then the history, to learn it is the third attempt. Then team chat, to ask if anyone saw this today. Then a knowledge base that may predate the last release.

The context exists. It sits in pieces that don't know about each other, so a person rebuilds it per ticket. Senior agents are fast because they carry the links in their heads: which release broke what, which team owns which screen, which workaround works. When they leave, the links leave.

The questions support asks are about connections. What did this customer try before? What fixed the last tickets like this? Which release caused this spike? Who has solved this before? So I stored the connections as a graph the agent can walk, instead of prose it has to re-read.

"I think" is not evidence. Most of what follows is me trying to prove myself wrong, and logging what that cost.

We want to know whether the graph earns its place. In mochi, one dataset and one question set go to six memory arms. Each arm gets the same model and the same judge:

Temporal invalidation with a sentinel, because FalkorDB can't store null

When a fact changes (the bug is fixed, the customer upgrades), how does memory forget the old fact without losing it?

We want a wrong fact retired, not erased. In mochi, every fact that can change is an edge with valid_from and valid_until. A contradiction closes the old edge with a date and creates a new one. Nothing is deleted.

My plan said "live means valid_until is null". FalkorDB disagreed: a property can't be null. SET r.x = null removes it, and IS NULL can't use an index. So a live edge carries a far-future sentinel, and one range filter serves both "now" and "as of last Tuesday":

// contracts/graph.ts
export const VALID_FOREVER = 253402300799000; // 9999-12-31
export const EDGE_AS_OF = (a) =>
  `${a}.valid_from <= $as_of AND ${a}.valid_until > $as_of`;

// gen/events.ts: a plan change retires the live edge, then creates the new one
OPTIONAL MATCH (c)-[e:ON_PLAN]->(p:Plan) WHERE ${EDGE_AS_OF('e')} AND p.name <> $to
FOREACH (x IN CASE WHEN e IS NULL THEN [] ELSE [e] END | SET x.valid_until = $as_of)
WITH c, np, count(e) AS retired
FOREACH (_ IN CASE WHEN retired > 0 THEN [1] ELSE [] END |
  CREATE (c)-[:ON_PLAN {valid_from:$as_of, valid_until:$forever}]->(np))
rejected
Python with Graphiti on FalkorDB, which gives temporal logic for free. Also "absent means live", which can't use an index.
cost
A magic number on every live edge. Every query must carry the as-of fragment, plus created_at <= $as_of on nodes. I wrote by hand the logic Graphiti would have given me. Now I can explain every line of it.

The database enforces the memory tiers, not the prompt

The company brain is shared and append-only. What stops a prompt-injected conversation from writing to it?

We want a shared brain that no conversation can quietly edit. In mochi, user conversations don't get the write tool, and FalkorDB refuses the write anyway. The ACL users are config, so they survive restarts:

# docker-compose.yml
--user mochi_reader ... resetkeys ~mochi_company ~team_* -@all
       +GRAPH.RO_QUERY +GRAPH.EXPLAIN +GRAPH.LIST +PING
--user mochi_dream  ... resetkeys ~mochi_company ~mochi_company_prev ~algo_scratch ~team_*
       -@all +GRAPH.QUERY +GRAPH.RO_QUERY +GRAPH.COPY +GRAPH.DELETE ...

The obvious grant, Redis's read-only key pattern %R~, breaks GRAPH.RO_QUERY, because that command's key spec is read-write. I caught this in a throwaway container before it reached the contract. The refusal test runs a write CREATE, a GRAPH.QUERY, a foreign graph and a GRAPH.DELETE as the reader. Refused: .

Trusting the tool loadout alone. The %R~ pattern. Runtime ACL SETUSER, which vanishes on restart.

Every number carries a receipt: query_id and $as_of

How does a reader check a number the agent shows them?

We want every figure to open the query that produced it. In mochi, every query result is stored as {id: "q_n", cypher, graph, params, rows}, and every stored query takes $as_of. A tool card, a chart or an inline number points at a query_id. A number without one fails validation. Because every query takes $as_of, a shared report link with ?asOf= re-runs the same Cypher at that time and shows what the brain believed then. That needed no per-query code.

/* mochi:likely_cause@v1 */
MATCH (t:Ticket {id: $ticketId})-[:ABOUT]->(i:Issue)<-[x:INTRODUCED]-(r:Release)
WHERE x.valid_from <= $as_of AND x.valid_until > $as_of
  AND t.created_at <= $as_of AND i.created_at <= $as_of AND r.created_at <= $as_of
RETURN t.id AS ticket, i.name AS issue, r.version AS release
ORDER BY r.shipped_at DESC, r.version LIMIT 3
rejected
Free text-to-Cypher as the main path. A query the model invents on the spot is hard to receipt honestly, and it makes FalkorDB easy to swap out, which breaks the competition's first rule.
cost
Every core query is hand-written and tested. At 14:51 I amended this: chat got query_graph, so the model can write its own Cypher for questions I didn't write a query for. It runs as GRAPH.RO_QUERY under the reader role, must take $as_of, and is stored as a q_n receipt with its exact text.

Sandboxed HTML, with no literal numbers

Some chat answers need a layout no component covers. How do I allow model-written HTML without allowing model-written figures?

We want the last-resort HTML path to obey the receipts rule too. In mochi, the guard rejects any digit in visible text outside a data-q="q_n" data-col="…" placeholder. The host fills each placeholder from the stored query rows before render. The guard also rejects any script, any network reference and any literal colour or font. The iframe gets sandbox="" and a CSP of default-src 'none'.

rejected
CopilotKit's open generative UI path, which is never enabled. JavaScript in the sandbox, because script can write any text, so "no literal numbers" could not be checked. A DOM sanitiser, which adds a dependency and still doesn't enforce receipts.
cost
"Release v2.4" in prose must come from a placeholder or be spelled out. Interactivity is limited to CSS and <details>. The guard is regex-based. The CSP is the real network barrier.
sun 12:11 · add-dream

The dream: one writer, eight steps, two LLM touchpoints

Who keeps the brain current, and how much of that work should a model do?

We want the brain to consolidate overnight and wake up knowing what changed. In mochi, the dream is a Pi Durable background task. It is the only writer of mochi_company, and it runs in order:

  1. Snapshot with GRAPH.COPY.
  2. Ingest the day's tickets.
  3. Apply due contradiction events.
  4. Cluster with algo.labelPropagation.
  5. Promote repeated fixes into practice.
  6. Run the doctrine-vs-practice rules.
  7. Commit taught policies.
  8. Write the morning report.

A model touches two steps: entity extraction, into a closed vocabulary from the contract, and two sentences of suggestion prose. Spotting a mismatch is arithmetic: a promised number in a KB article against a measured number from tickets, in Cypher.

rejected
A cron job bolted on. Asking an LLM to spot contradictions. Updating pattern nodes in place, which breaks as-of reads. Running community detection on the live graph, because algorithms ignore edge properties and would count retired edges.
cost
A scratch projection graph for every clustering run. Label propagation on a Ticket–Issue graph collapses to roughly one cluster per issue. I accepted that for the nightly report, and the clusters entry below says what that means. In Pi Durable 1.3.0 a sleeping background task can mark its conversation busy, so the demo path is "run dream now". The mismatch ablation (rules against an LLM reading all the text) is in the ledger below.

sun 16:32 · falkordb-storage

FalkorDB as Pi Durable's journal

The memory lives in FalkorDB. The agent's own history lives in SQLite. Can one database hold both?

We want the agent's own history to be walkable, like its memory. In mochi, MOCHI_STORAGE=falkordb swaps Pi Durable's storage for agent/storage/falkordb.ts, which writes the mochi_journal graph. Each commit batch is one parameterised write, atomic in FalkorDB. A Journal counter node issues the commit sequence in the same query. A forked conversation is a FORKED_FROM edge. The trace_story tool walks the journal as mochi_reader, which can read it and never write it.

The upstream Pi Durable storage conformance suite passes against it, and the crash test resumes on it. That is demonstrated, not benchmarked. bench/results.json has no row for it, so I quote no number.

rejected
Making it the default on deadline day. Writing my own harness storage from scratch instead of implementing Pi Durable's Storage interface.
cost
It ships off by default. SQLite stays the default journal. Production must run --appendfsync always, or a crash can lose a committed step. One more graph in the ACL config.

Decision traces: learning from past tickets without a pile of stale notes

Can the agent learn from past tickets without growing a pile of stale notes?

We want the agent to reuse what worked last time, and to drop it the moment its facts stop being true. In mochi, every answer that worked becomes a trace in the mochi_traces graph: Trace, Step and Query nodes, with the receipts it used. A new ticket finds similar resolved tickets through SIMILAR_TO, then replays their stored queries, so the model reads rows instead of exploring. Before replay, every receipt is re-checked at the current $as_of. A trace whose facts were retired is closed and never offered again.

I tested it against five other ways to learn. Each one learned from the same earlier resolved tickets, with the same facts per lesson. Each answered the same later tickets. Then I retired facts and checked whether stale fixes came back.

  • Graph traces, replayed as above.
  • Graph memory, no learning: plain arm D.
  • Markdown + LESSONS.md: arm C with an append-only lessons file.
  • Devin-style Knowledge: trigger and content entries. It is modelled on Devin's documented Knowledge feature, not Devin itself.
  • Vector lessons: top-3 lessons by embedding.
  • SQL lessons: a lessons table the model queries with one read-only SELECT.

Traces got right at per 1,000 answers. No learning: at . Replay is cheaper because the model reads input tokens instead of , in one model call instead of two.

    The crash test

    We want an always-on agent to survive dying. In mochi, every step of a run is a Pi Durable checkpoint.

    1. A ticket arrives with a fixed requestId, and the agent starts its briefing.
    2. The script sends kill -9 after the first tool call.
    3. A new process opens the same storage and calls harness.resume().
    4. Read tools are replay: "safe" and re-run. Write tools are never silently repeated: the model is told the call was interrupted.
    5. The same requestId returns the original submission's answer. The graph never noticed.

    This is demonstrated, not benchmarked, and the ledger says so. To see it, run npm run crash-demo -w agent (agent/scripts/crash-demo.ts).

    FAQ

    Why not just a vector database?
    I tried. It is arm B. See fig 6.
    Why not just Postgres?
    I tried SQLite. It is arm E, and it gets the same five queries as SQL. It came second. Tables are a fair rival.
    Is this a shot at Devin?
    No. Arm C implements the open Agent Memory Repo spec, not Devin the product. The Devin-style Knowledge approach is modelled on Devin's documented Knowledge feature, not Devin itself. Both are good at what they are for: preferences and project gotchas. Support context has a different shape.
    Why is there a SQLite file in a graph project?
    By default, two jobs. FalkorDB holds what the agent knows. SQLite holds what the agent is doing: Pi Durable's transcripts and checkpoints. With MOCHI_STORAGE=falkordb, that journal moves into FalkorDB too.
    Is any of the data real?
    No. E Corp Securities is fictional. The generator is seeded and in the repo. The helpdesk's shape comes from public Freshdesk docs. No real ticket was read, copied or used as an example.
    What if the dream is wrong?
    It retires, it never deletes. Yesterday's brain is a GRAPH.COPY, and any report can be re-run with ?asOf=. Suggestions are hypotheses with ticket IDs attached. Nothing applies them automatically.

    Use of AI
