One build day, logged: what we chose, what we rejected, what it cost

This is the decision log of one build day. The repo got its first commit at 10:35 IST. Each entry below has a timestamp from the git history, the question we faced, what we rejected, and what it cost. Every figure on this page is read from bench/results.json. Figures the benchmark has not produced yet say pending. The code is at github.com/AtharvaMaskar/mochi-ai.

The problem

We want a support agent to start every ticket knowing what the company already knows. In mochi, the agent gets a briefing before it types a word.

Watch a support agent take a ticket. "Money deducted, order not placed." Before they can write anything useful, they open the CRM to see who this is. Then billing, to confirm the debit. Then the history, to learn it is the third attempt. Then team chat, to ask if anyone saw this today. Then a knowledge base that may predate the last release.

The context exists. It is stored in pieces that do not know about each other, so a person reassembles it per ticket. Senior agents are fast because they carry the links in their heads: which release broke what, which team owns which screen, which workaround works. When they leave, the links leave.

The questions support asks are about connections. What did this customer try before? What fixed the last tickets like this one? Which release caused this spike? Who has solved this before? So we stored the connections as a graph the agent can walk, instead of prose it has to re-read.

"We think" is not evidence. Most of what follows is us trying to prove ourselves wrong, and logging what that cost.

sun 12:31 · amended from the sat plan

Graph, markdown, vector or SQLite

Is a graph the right memory, or would a folder of markdown, a vector index, or plain tables do the same job?

We want to know whether the graph earns its place. In mochi, one dataset and one question set go to six memory arms. Each arm uses the same model and the same judge:

  • A puts everything in the prompt.
  • B is vector top-k, stored in FalkorDB's own vector index so that only the traversal differs from D.
  • C is markdown file memory: an implementation of the open Agent Memory Repo spec, with a MEMORY.md index and a nightly rewrite.
  • D is the graph: five hand-written Cypher queries.
  • E holds the same data in SQLite, with SQL tools that mirror D one for one.
  • F is TencentDB Agent Memory, time-boxed.

E was added at 12:31. It is the arm most likely to embarrass us. If tables with joins answer as well as edges, then the win is "structured storage", not "graph", and we should say so.

rejected
Asserting the graph is better. Benchmarking only against a stuffed prompt, which any structured store beats.
cost
The afternoon, a hard spend cap on npm run bench -- --max-usd, and an arm that can beat D. Arm F is reported "not measured" if it has no clean Node adapter after the time box. It is never faked.
sun 11:27 · add-contracts

Temporal invalidation with a sentinel, because FalkorDB can't store null

When a fact changes (the bug is fixed, the customer upgrades), how does memory forget the old fact without losing it?

We want a wrong fact retired, not erased. In mochi, every mutable fact is an edge with valid_from and valid_until. A contradiction sets valid_until on the old edge and creates a new one. Nothing is deleted.

The plan said "live means valid_until is null". FalkorDB disagreed: a property cannot be null. SET r.x = null removes it, and IS NULL cannot use an index. So a live edge carries a far-future sentinel, and one range filter serves both "now" and "as of last Tuesday":

// contracts/graph.ts
export const VALID_FOREVER = 253402300799000; // 9999-12-31
export const EDGE_AS_OF = (a) =>
  `${a}.valid_from <= $as_of AND ${a}.valid_until > $as_of`;

// gen/events.ts: a plan change retires the live edge, then creates the new one
OPTIONAL MATCH (c)-[e:ON_PLAN]->(p:Plan) WHERE ${EDGE_AS_OF('e')} AND p.name <> $to
FOREACH (x IN CASE WHEN e IS NULL THEN [] ELSE [e] END | SET x.valid_until = $as_of)
WITH c, np, count(e) AS retired
FOREACH (_ IN CASE WHEN retired > 0 THEN [1] ELSE [] END |
  CREATE (c)-[:ON_PLAN {valid_from:$as_of, valid_until:$forever}]->(np))
rejected
Python with Graphiti on FalkorDB, which gives temporal logic for free. Also "absent means live", which cannot use an index.
cost
A magic number on every live edge. Every query must carry the as-of fragment, plus created_at <= $as_of on nodes. We wrote by hand the logic Graphiti would have given us, and we can now explain every line of it.
sun 11:27 · add-contracts

The database enforces the memory tiers, not the prompt

The company brain is shared and append-only. What stops a prompt-injected conversation from writing to it?

We want a shared brain that no conversation can quietly edit. In mochi, the tool loadout leaves the write tool out of user conversations, and FalkorDB refuses the write anyway. The ACL users are config, so they survive restarts:

# docker-compose.yml
--user mochi_reader ... resetkeys ~mochi_company ~team_* -@all
       +GRAPH.RO_QUERY +GRAPH.EXPLAIN +GRAPH.LIST +PING
--user mochi_dream  ... resetkeys ~mochi_company ~mochi_company_prev ~algo_scratch ~team_*
       -@all +GRAPH.QUERY +GRAPH.RO_QUERY +GRAPH.COPY +GRAPH.DELETE ...

The obvious grant, Redis's read-only key pattern %R~, breaks GRAPH.RO_QUERY, because that command's key spec is read-write. We found this in a throwaway container before it reached the contract. The refusal test runs a write CREATE, a GRAPH.QUERY, a foreign graph and a GRAPH.DELETE as the reader. Refused: .

rejected
Trusting the tool loadout alone. The %R~ pattern. Runtime ACL SETUSER, which vanishes on restart.
cost
Three connection roles in every process. Per-command grants that we maintain by hand. A teach tool that cannot write the brain directly, so it files candidates in a team graph for the dream to commit.
sun 11:27 · add-contracts, wired 12:15 in add-agent-core

Every number carries a receipt: query_id and $as_of

How does a reader check a number the agent shows them?

We want every figure to open the query that produced it. In mochi, every query result is stored as {id: "q_n", cypher, graph, params, rows}, and every stored query must take $as_of. A tool card, a chart or an inline number references a query_id. A number without one fails validation. Because every stored query takes $as_of, a shared report link with ?asOf= re-runs the same Cypher at that time and shows what the brain believed then. That needed no per-query code.

/* mochi:likely_cause@v1 */
MATCH (t:Ticket {id: $ticketId})-[:ABOUT]->(i:Issue)<-[x:INTRODUCED]-(r:Release)
WHERE x.valid_from <= $as_of AND x.valid_until > $as_of
  AND t.created_at <= $as_of AND i.created_at <= $as_of AND r.created_at <= $as_of
RETURN t.id AS ticket, i.name AS issue, r.version AS release
ORDER BY r.shipped_at DESC, r.version LIMIT 3
rejected
Text-to-Cypher. A query the model invents on the spot cannot be receipted honestly, and it makes FalkorDB optional, which breaks the competition's first rule.
cost
Every query is hand-written and tested. The agent cannot answer a shape of question we did not write a query for. It says so, instead of guessing.
sun 11:27 · add-contracts

Stories in nao's format: markdown plus tags that point at query results

The dream writes a morning report, and users ask for dashboards. Who draws them, and where do their numbers come from?

We want reports that a model writes and a renderer draws, with no model-written data. In mochi, a story is markdown plus self-closing tags (<kpi>, <bars>, <line>, <table>, <memdiff>, <suggestion>, <num>), and each tag names a query_id and its columns. The format is borrowed from nao's story-segments.ts. One parser in contracts/ serves both the producers and the renderer, so they cannot drift.

Median resolution is <num query_id="q_1" column="median_h">…</num> hours.
<bars query_id="q_2" label="Emerging clusters" x="cluster" y="tickets"/>
rejected
Letting the model write HTML or chart JSON. Separate schemas for each card type.
cost
The model can only draw what we have a tag for. A story that names an unknown query is rejected, not rendered, and the producer pays for a retry.
sun 11:35 · add-chat-contracts

Sandboxed HTML, with no literal numbers

Some chat answers need a layout no component covers. How do we allow model-written HTML without allowing model-written figures?

We want the last-resort HTML path to obey the receipts rule too. In mochi, the guard rejects any digit in visible text outside a data-q="q_n" data-col="…" placeholder. The host fills each placeholder from the stored query rows before render. The guard also rejects any script, any network reference and any literal colour or font. The iframe gets sandbox="" and a CSP of default-src 'none'.

rejected
CopilotKit's open generative UI path, which is never enabled. JavaScript in the sandbox, because script can write any text, so "no literal numbers" could not be checked. A DOM sanitiser, which adds a dependency and still does not enforce receipts.
cost
"Release v2.4" in prose must come from a placeholder or be spelled out. Interactivity is limited to CSS and <details>. The guard is regex-based; the CSP is the real network barrier.
sun 12:11 · add-dream

The dream: one writer, eight steps, two LLM touchpoints

Who keeps the brain current, and how much of that work should a model do?

We want the brain to consolidate overnight and wake up knowing what changed. In mochi, the dream is a Pi Durable background task. It is the only writer of mochi_company, and it runs in order:

  1. Snapshot with GRAPH.COPY.
  2. Ingest the day's tickets.
  3. Apply due contradiction events.
  4. Cluster with algo.labelPropagation.
  5. Promote repeated fixes into practice.
  6. Run the doctrine-vs-practice rules.
  7. Commit taught policies.
  8. Write the morning report.

A model touches two steps: entity extraction, into a closed vocabulary from the contract, and two sentences of suggestion prose. Detecting a mismatch is arithmetic: a promised number in a KB article against a measured number from tickets, in Cypher.

rejected
A cron job bolted on. Asking an LLM to spot contradictions. Updating pattern nodes in place, which breaks as-of reads. Running community detection on the live graph, because algorithms ignore edge properties and would count retired edges.
cost
A scratch projection graph for every clustering run. Label propagation on a bipartite Ticket–Issue graph collapses to roughly one cluster per issue, and we accepted that. In Pi Durable 1.3.0, a sleeping background task may mark its conversation busy, so the demo path is "run dream now". The mismatch ablation (rules vs an LLM reading all the text) is in the ledger below.

If the graph does the remembering, how small can the model be?

We want the memory to carry the weight, not the model. In mochi, MOCHI_MODEL defaults to claude-haiku-5-5, and every arm also runs on claude-sonnet-5-5. The question the sweep answers: can Haiku on the graph match Sonnet on markdown? Haiku on D scored at per task. Sonnet on C scored at per task.

A Sonnet default, which is the comfortable choice for a demo.
cost
A weaker reader of hard questions in the live product. The sweep roughly doubles benchmark spend. The judge is a third model, claude-opus-5-5, with a 3-vote majority on every multi-hop and structural answer.

What number should a reader compare across arms?

We want the number a team would pay. In mochi, a task is one eval question answered the way the agent would answer it, tool calls included. sun 13:27 · amend-contracts-3, add-sim

A simulated helpdesk instead of a desk API on the graph

Where do tickets come from in the demo, and how real does their mess need to be?

We want Mochi to integrate with something shaped like a real helpdesk. In mochi, a fictional Freshdesk-shaped sim for E Corp Securities serves tickets over a REST API, with webhooks and a replay clock. The mail is messy: follow-ups, merges, CCs, auto-reply loops, bounces, spam, Hinglish and wrong requesters. Its shape comes from public Freshdesk docs only. Mochi gets a webhook, fetches the ticket, writes it pending, and the dream ingests it. Facts never pass through a model: templates fix every fact, and Haiku only rewords tone, behind a committed cache.

rejected
A bespoke desk API on top of the graph. A second, separate sim world, which would give two truths. Any real helpdesk data, which the rules forbid and we would not use anyway.
cost
A third serial contract change mid-day, a webhook listener with a sweep, a replay clock, and noise filters at ingest. The graph, the eval and the benchmark now derive from one truth file.

The scale cut: benchmark a fixed slice, not the whole sim

The sim renders thousands of tickets. Do we benchmark all of them?

We want benchmark numbers we can afford to re-run. In mochi, the benchmark runs on a fixed, seeded slice of the sim that keeps every planted structure: both bad-release spikes, the stale KB articles, the undocumented workarounds, the follow-up chains and a merge cluster. The graph the benchmark ran against held nodes and edges.

The crash test

We want an always-on agent to survive dying. In mochi, every step of a run is a Pi Durable checkpoint in SQLite.

  1. A ticket arrives with a fixed requestId, and the agent starts its briefing.
  2. The script sends kill -9 after the first tool call.
  3. A new process opens the same storage and calls harness.resume().
  4. Read tools are replay: "safe" and re-run. Write tools are never silently repeated: the model is told the call was interrupted.
  5. The same requestId returns the original submission's answer. The graph never noticed.

This is demonstrated, not benchmarked, and the ledger says so. The clip is in the demo video.

FAQ

Why not just a vector database?
We tried. It is arm B. See fig 5.
Why not just Postgres?
We tried SQLite. It is arm E, and it gets the same five queries as SQL. If it ties, we will say the graph's advantage was structure, not edges.
Is this a shot at Devin?
No. Arm C implements the open Agent Memory Repo spec, not Devin the product. That spec is good at what it is for: preferences and project gotchas. Support context has a different shape.
Why is there a SQLite file in a graph project?
Two jobs. FalkorDB holds what the agent knows. SQLite holds what the agent is doing: Pi Durable's transcripts and checkpoints, which the crash test runs on. We did not hand-roll storage under our own crash demo.
Is any of the data real?
No. E Corp Securities is fictional. The generator is seeded and in the repo. The helpdesk's shape comes from public Freshdesk docs, and no real ticket was read, copied or used as an example.
What if the dream is wrong?
It retires, it never deletes. Yesterday's brain is a GRAPH.COPY, and any report can be re-run with ?asOf=. Suggestions are hypotheses with ticket IDs attached. They are never applied automatically.

How this was built

AI coding assistants built most of this repo, as the rules allow, and we disclose it here and in the README. We used Claude Code on Claude Opus 5.5. Parallel agents each worked in their own git worktree, one OpenSpec change per worktree: propose, apply, archive. Contracts froze first, and every later contract change was serial. This post was drafted by an agent from the archived changes and the git log, then reviewed by us. We can explain every graph model, query and decision on this page. The figures come from bench/results.json through blog/fill-bench.ts, which refuses to fill the page while any marker is left.
